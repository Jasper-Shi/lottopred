3. entry成功后按新精确phase序列完成单次lease、checkpoint、claim、科学ledger和history-load-intent；checkpoint先于claim，最终startup seal另被manifest绑定，避免自哈希环。新phase数/checkpoint序号必须从新事件表推导，不能硬套13/9/12。
4. history/input准备通过后，在**任何首次模型生成调用（包括其特征计算）之前**写入并fsync `first_forecast_generation_intent`；绑定target ordinal/date、前缀摘要、模型/selector版本、source/core/closure、唯一attempt ID。这不是预测成功的声明，只是不可重试阶段边界。
5. 每个后续target也先有新注册的 durable generation-intent。不存在“上期已完成所以本期可无记录调用”的例外。模型被调用一次后概率验收失败，不允许用公平值、修补值或重新计算替代。
6. 保存生成结束的真实UTC与完整五组快照；冻结成功回执与hash链/fsync确认在前，目标reveal在后。揭晓前的intent及成功receipt、独立评分完成事件应明确，使零完成评分时也能区分未生成、已生成未冻结、已冻结未揭晓、已揭晓未评分。无法证明的阶段记unknown，不从缺少成功receipt反推副作用未发生。

正式entry确认、首次generation-intent和每个reveal/score事件的精确payload、格式、计数、时间关系、异常终止/terminal外部观察绑定，必须在R先注册并合成故障测试。不能运行后根据0行/半个文件补定义。若durable错误日志也写不下，保留所有已存字节和真实外部终止观察，禁止跳到未注册新日志路径或重试worker来补日志。

## 7. 五组冻结、评分、capture 与 null schema 的变化

不能复用 V13 的 `four_forecasts`、四producer排序、按model_name一组Final6、旧Top12精确检验、Holm或十gates。新完整冻结单位是**一份49概率/hex + 全49排序 + Top6/12/18/30 + 固定ID顺序G1..G5全部五组 + 元数据**；组内排序、两两不重叠、并集Top30、五组各六号在reveal前全部验收。旧final_combination仅等于G1，final_6_hits仅等于H1，不能后验把赢家换进去。

每期一次冻结的hash须绑定概率源/新实验/selector/特征版本、真实生成/冻结时间、输入prefix/截止、R/I/K/A/M/L、运行时和所有5组；ledger外层保存全payload或注册的不可变快照引用，不能只记录获胜组。全部五组和概率评分完成后才决定是否停止下一target。

capture身份至少绑定新实验/模型/selector、target日期、固定group_ID、sorted6、整个五组forecast_sha、claim/ledger/W/M与审计身份；G1–G5是唯一capture namespace。Top6/Top12/Top18不是额外票；没有隐藏V1/random票。机会唯一身份应以实验内target+sorted6保持去重，并保留group_ID，不将跨版本重复日期或重复票累加成新的独立证据。joint-probability字段不适用，不能填Σp/∏p冒充。

新终态与推断字段必须与科学v2一一对应：

| 已知持久阶段/科学条件 | 终态约束 | 推断字段 |

| entry已进入、首次生成意图前失败，且有积极证明模型从未开始 | startup_failed_unscored_no_retry，科学分类null | aggregate/两半p、12CI、通过均null |

## 8. artifact、独立audit、普通发布与默认通知

可以继续采用原始worker artifact为M单父、独立临时index、原主index/HEAD不变、精确新ADD的模式。新entry若与startup同文件，第一生成意图在ledger，通常仍可保持claim/startup/ledger/JSON/Markdown/manifest六个最终角色；但若新增entry/terminal独立文件，须在R明确新增角色/路径/count并调整所有权、manifest、审计和publication。不能先假定六文件或沿用V13 event/key count。

每类JSON是否C或C+LF、科学事件hash是否排除自身hash字段、startup/journal完整LF链、raw/API GET/POST message framing、浮点hex、Markdown字节渲染均逐项注册。保留V13非循环原则：早期checkpoint→claim→ledger，最后manifest绑定封闭startup和其他输出，W再绑定manifest；manifest不自包含自己的SHA或未来W。schema required_keys 和 count 必须由新字段集合算出，拒绝缺键、多键、bool混int、非finite或未知enum。

正式worker结束后只读审核冻结事实：原概率/rank/G1–G5 equality oracle、真实prefix/actual、计分算术/全部摘要、phase/ownership/lease/Git/runtime都核查；不得refit/生成替代组/再consume。原始W通过独立两轴、准确head CI后普通PR发布，不rewrite/squash/rebase。完整negative尝试审计闭合后，才可在另一个普通状态文档PR说明关闭、保存旧immutable生成状态。

capture有更严格顺序：原W保持→独立leakage audit→新固定candidate bundle + audit JSON/MD→准确源CI/双轴→普通受保护main发布→只读重新验证该发布、原M/W/原lease/runtime→新独占通知意图和远端一次标记→持久化send-intent→最多一次默认send→保存sent/failed/unknown。group ID、完整五组hash和“预冻结五组之一的历史6/6”必须贯穿bundle/audit/邮件，不能沿用V13“若干producer共享一张票”的身份。

默认SMTP边界：仅调用不变的 `notification.send_email(subject,body)`（源码:13），由仓库已审默认Secrets路线在授权发送进程内存注入SMTP_USERNAME/PASSWORD；注册/审查/helper不得读取、显示、复制或记录Secret。底层旧sender虽然支持四个环境override，但新上层必须如V13 :6165、:9480、:9573那样在准备及发送前拒绝SMTP_HOST/SMTP_PORT/EMAIL_FROM/EMAIL_TO，不能允许调用参数替换收件人、服务器、sender或transport。消息从已验证capture事实构建，不接受调用者自定义文本。

通知必须有独立purpose capability和全局一次标记，不能因为历史lease已存在就自行获得send权限。发送失败/异常/未知、send-intent已写或createRef结果不确定都永久停止；不重发、不重跑worker、不删除/更新通知标记。缺少正常Secrets注入路线是事前要解决的真实操作缺口，不能临时读取Secret补救。普通小时进度邮件另走已审committed-state路线，每小时任何成功/失败尝试均去重；不能用进度邮件冒充capture通知，也不能因新agent接手重复发送。

## 9. current-head preservation 对 capture 路线的实际影响

V13 `_registered_authorities` :3144在origin与当前head检查整个旧preserved tree，而不只是runtime源码。旧seal记录：ARCHITECTURE blob `0170afb96bb54375fb90f73107b36a76ad79bcc3`、OPERATIONS blob `062ff6bf905d116fe379d09b36e242a6d44a72fa`；观察924a的对应blob为 `4ced65f8c861e37369b4b0afb425dfc1ee92eb55` 与 `8653120ab7dcfd81c34db4c71b3620a56870c068`。这些是源码树元数据观察，不是重新执行旧verifier或读取结果。

因此旧V13 native current-head verifier在这样的文档闭合head不再适合作通用入口；这不撤销已完成旧尝试的历史证据，更不使其获得重试权。新R应从实际选择的新base建立自己的preservation，不把旧base manifest当新base。

新capture的audit/publication/notification必须在保持新R冻结baseline/runtime的拓扑内完成：预先允许的新增bundle/audit/通知文件可加入，但不得在发送完成前随意改ARCH/OPER或其他preserved路径。`verify_notification_publication` :8856要求精确当前main普通合并与固定source ADD集合；`:9480`发送前再次核对当前main/原文件/runtime。途中状态文档合并、package/config修改或main漂移会阻断通知，不能在看到capture后放宽verifier救活。

可操作安排是把状态文档更新延后至已完成/已永久终止的通知分支；或在新R事前定义一条严格、更一般但仍不可变可审计的publication拓扑并独立测试。本文推荐保留前者的简单冻结顺序，不在结果后新增豁免。完整negative路线没有capture通知待完成，关闭尝试后可单独普通PR更新状态。所有未来live/workflow/CLI/scheduler接线继续未授权；本历史设计不恢复任何过期日期或lane。
